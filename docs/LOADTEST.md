# Навантажувальний сценарій

Сценарій: `loadtest/notes.js`. Запуск однією командою `k6 run`.

## Профіль

Один віртуальний користувач в ітерації:

1. `POST /notes` — один запис (потрібен JWT).
2. Дев'ять читань: список, щойно створена нотатка за id, дані автора, і ще кілька повторів тих самих читань.

Співвідношення читання до запису — 9:1. Список, картка і автор повторюються, щоб було що знімати з кешу.

## Фази

| Фаза | Тривалість | Користувачі |
|---|---|---|
| Наростання | 3 хв | від 0 до N |
| Плато | 5 хв | N |
| Спад | 2 хв | від N до 0 |

Разом 10 хвилин. N за замовчуванням — 15 (`VUS`). Розрахунок, чому цього має вистачити для масштабування, — у `docs/AUTOSCALING.md`.

Наростання потрібне, щоб не вдарити в один холодний екземпляр усіма користувачами одразу: інакше перші хвилини — це 5xx і черга, а не вимір робочої системи. На графіку тоді видно схил, перетин цілі і появу машин, а не одну вертикальну стіну.

## Команда

```bash
k6 run --summary-export loadtest/summary.json \
  -e BASE_URL=http://<alb-dns> \
  -e ADMIN_PASSWORD='...' \
  -e VUS=15 \
  loadtest/notes.js
```

`ADMIN_USERNAME` за замовчуванням `admin` (передається так само, через `-e`). Якщо `k6` немає локально, та сама команда всередині контейнера:

```bash
docker run --rm -v "$PWD:/work" -w /work grafana/k6:0.54.0 run \
  --summary-export /work/loadtest/summary.json \
  -e BASE_URL=http://<alb-dns> -e ADMIN_PASSWORD='...' -e VUS=15 loadtest/notes.js
```

Після прогону сирий звіт лежить у `loadtest/summary.json` (файл у `.gitignore`).

## Як читати підсумок k6

- Кількість запитів — `http_reqs` (count).
- Частка помилок — `http_req_failed` (rate).
- Латентність: `http_req_duration` → `p(50)`, `p(95)`, `p(99)`. У k6 p50 — це і є медіана.
- Влучання в кеш — лічильники `cache_hits` і `cache_misses` (лише читання з заголовком `X-Cache`).

p50 — типовий користувач. p95 і p99 — повільний хвіст. Середнє ховає цей хвіст: тисяча швидких відповідей і кілька таймаутів дають «нормальне» середнє, хоча частина людей чекала секунди.

Кількість запитів за секунду — це пропускна здатність. Кількість одночасних користувачів — це паралелізм. Вони зв'язані через латентність: `користувачі ≈ RPS × час_відповіді`. Якщо відповідь стає повільнішою, ті самі користувачі дають менше RPS, бо кожен довше тримає свою ітерацію.

## Результати

Вставити після реального прогону. Не заповнювати оцінкою.

| | Запитів | Частка помилок | p50 | p95 | p99 |
|---|---|---|---|---|---|
| N = 15, кеш увімкнений | | | | | |
| N = 15, кеш вимкнений | | | | | |

Як вимкнути кеш для другого рядка — у `docs/CACHE.md`. Після кожного прогону дочекатися, поки група повернеться до мінімуму (1 вночі, або 2 якщо вже спрацював денний розклад), і лише тоді запускати наступний.
