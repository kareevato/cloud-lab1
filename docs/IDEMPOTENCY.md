# Ідемпотентний запис

`POST /notes` приймає заголовок `Idempotency-Key`.

- Перший запит із ключем створює нотатку і кладе готовий JSON відповіді в Redis на 24 години (`idem:<ключ>`).
- Повтор із тим самим ключем не пише в базу. Відповідь та сама, плюс заголовок `Idempotent-Replayed: true`.
- Без заголовка кожен POST — новий рядок. Так і має бути.

Перевірка двома однаковими запитами:

```bash
BASE_URL=http://<alb-dns> ADMIN_PASSWORD='...' ./loadtest/idempotency.sh
```

Очікування: один `id` у двох тілах, другий відповідь з `Idempotent-Replayed: true`, у списку один такий запис.

Юніт-тест `test_idempotency_key_does_not_insert_twice` робить те саме локально.

## Яку проблему це закриває

Клієнт повторив запит, бо не дочекався відповіді або користувач двічі натиснув «зберегти». Без ключа в базі два однакові записи. З ключем повтор повертає результат першого виконання.

Якщо Redis недоступний, заголовок ігнорується і запис все одно виконується. Інакше падіння кешу зупинило б створення нотаток. Гарантія ідемпотентності в цей момент слабша за доступність. Це варто сказати на захисті прямо.

## Зв'язок із чергою

Асинхронний шлях не використовує цей заголовок. Його ідемпотентність — `job_id`: повторна доставка SQS бачить job у статусі `done` і не вставляє нотатку вдруге (`docs/QUEUE.md`).

Разом: ключ клієнта захищає від подвійного HTTP-запиту, а статус job — від подвійної доставки повідомлення. Це різні межі однієї проблеми. Якби `POST /notes/async` теж приймав `Idempotency-Key`, повторний HTTP не створював би другий job; зараз повторний HTTP створить другу роботу, а дубль уже всередині черги — ні.

Методи, ідемпотентні за специфікацією HTTP самі по собі: GET, HEAD, PUT, DELETE, OPTIONS. POST таким не є, тому ключ потрібен саме йому.
